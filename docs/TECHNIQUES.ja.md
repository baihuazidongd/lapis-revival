# 技術文書 · 成功パスと判定根拠

この文書に載るのは**再実行で証明できるものだけ**。各項目に判定根拠（ログ行、プロトコル ID、ハッシュ、スクリーンショット名）を付けた。
実測で覆された旧結論はすべて「訂正」として書く。遠回りの記録自体がこの文書の価値だからだ。

---

## 1. 全体方針：Lua には触らない、データとネットワークで解決する

クライアントには完全性防御が 2 層あり、これがプロジェクト全体の技術路線を決めた。

1. **Lua は内容バインドの trailer 付き**。`.lua` アセットの末尾に 32 ビット 16 進のチェック値が付く。ロード時に
   `LuaResLoader:DecryptLuaFile` → MD5 比較、不一致なら `LuaException: MD5 VERIFY FAILED`。
   1,239 個のアセット × 340 パターンの framings/salts、全部試してヒットゼロ：**アルゴリズム不明、Lua をその場で書き換えるのは不可**。
   「スクリプト 1 行直す」系の案はすべて不成立。データ側・アセット側・ネットワーク側で解決するしかない。
2. **本体データは実行時 SQLite**。`luaData/*.lua` は実体はローダで、`select * from <表>` を実行している。
   つまり挙動スイッチは**コードではなくデータ**（例：`Config` テーブルの `ShopFirstLook`、`Guideshow.Popup`）。

路線は結果的に 3 本柱に固定される。

| 柱 | 何を変えるか | 完全性をどう通すか |
| --- | --- | --- |
| ネットワーク | 端末内 Java サービススタブがプロトコルに応答 | クライアントはセッション鍵のみ検証、内容の意味は検証しない |
| データ | `master_data.db` / `master_data_lang.db` | `Seed.java` に SHA-1 をピン留め。DB を変えたらピンも同時に変更が必須 |
| アセット | `.bdl` の再パッケージ | 40 バイトの `.bdl.hash` サイドカー + manifest の Hash/Size 手術 |

## 2. プロトコルスタブ

- 分岐は 18 本、`ProtobufCore.call` の中で番号に従ってディスパッチ。重要番号：
  `P11` プレイヤー概要、`P120` ショップ一覧、`P121` 購入、`P132` イベント操作、`P200` アリーナ出撃、
  `P204` アリーナ精算、`P1016` 注意書き既読、`P1024` ガチャ。
- **どのページにいるかはプロトコルでしか判定できない**。`P9000` + `P1021` は 60 秒のハートビートで、
  どのボタンを押しても発火する。これを「ページ遷移成功」の根拠にすると完全に誤った結論になる。
- 判定根拠の書き方：`logcat -c` → シングルタップ → 待機 → プロトコル番号の数 + `LuaException` カウント + スクリーンショット。
  `tools/drive2.sh` 参照。

## 3. セーブデータと永続化

単一ファイル `/data/data/com.klab.lapis/shared_prefs/lapis_state.xml`（`ProtobufCore.java` の
`getSharedPreferences("lapis_state", 0)`）。キー系列：

```
wal_*        货币（辉圣石/金币/体力）        goods_<id>   每个商品已购数量（→库存角标/售罄）
itm_*        获得的道具                      stage_*      关卡通关与星级
pvp_score    竞技场积分                       av_*         换装间（owned/mode/cur/bind/name）
```

- コード全体を見ても `clear()` / `remove()` でこのストレージに触る箇所はゼロ。唯一の `.delete()` は `Seed` が自分の一時展開ファイルを消す処理。
- セーブが飛ぶのは以下だけ：アンインストール、`pm clear`、エミュレータインスタンスのリセット、**署名が変わった APK**。同一署名の `adb install -r` では飛ばない。
- クライアント側の通貨は `PlayerInst`（シードフィールド `diamondPay`）を読む。`items[]` に `P_*` 型を突っ込んでも無効。
  機能解放は `Newbie`（レベルまたはクリア済みステージ）を読む。

## 4. ショップ：一見手詰まりに見えたクラッシュ、真因はサーバー側タイムスタンプ

**症状**：ホームで購買部をタップ → 7〜8 回連続クラッシュ、ショップ UI は一切出ない。クラッシュスタックは固定：

```
LuaException: Object reference not set to an instance of an object.
  [C]: in function 'GetChildGameObject'
  PageShop.lua:555: in function 'InitScrollView'
  PageShop.lua:390: in function 'OnEnter'
  UIPanel.lua:216 DealWithEnter / :245 DealWithParentEnter / :231 DealWithEnter / :198 / :165
```

**歩んだ遠回り（全部実測で覆された。もう歩かないこと）**：

1. `UpdateTag` のいずれかの分岐が `SafeArea/Main/ScrollArea` を `SetActive(false)` しているのではと思った
   （`ScrollAreaMain` と `ScrollAreaGrid` が同一ノードをキャッシュしている）。そこでデータ側で着地タブを変更：
   Type 6 の行の `TabIndex` を動かし、`shopTab` の**発行順**を制御（`ShopManager.SetData` は後勝ち上書き：
   `listAllIndex[TabIndex]=Type`、`listAllType[Type]=TabIndex`）。3 パターン——アイテムに着地、交換所に着地、
   6 タイプ全部を同一の安全スロットに着地——**クラッシュスタックは一文字も変わらなかった**。
2. prefab のノード欠けを疑った。UnityPy でツリーを辿ると `PageShop/SafeArea/Main/ScrollArea` は存在、`active=True`、
   ツリー内で一意。端末とホストの bundle はバイト単位で一致。除外。

**真因**：`OnUpdateSecond`。`shop.json` の各行の `freshAt` は**パッケージ時点の値**で、とっくに過ぎている。
`freshAt - サーバー時刻 <= 0` になるとクライアントは `Fire("CloseRecharge")` → `OnBack()` → `Close()` →
`UIPanel.Purge` で `UIRootObject` を `nil` にする。`UpdateTag` 自身にはこの手を止める
`if self.closed then return end` があるが、`OnEnter` にはない。だから次の文、`InitScrollView` の
`GetChildGameObject` が `nil` を受け取って .NET の null 参照例外を投げる。

**修正**：サービススタブの出口で各行の `freshAt` を強制 `0`（意味は「二度と更新しない」。JP ショップ自身が `freshAt = 0` を使っている）。

**副作用（既知、直すかは任意）**：デイリー限定が翌日回復しなくなる。日付跨界が要るなら `P1016`/`UpdateServerRefresh`
で**未来**の更新時点を返し、日付で `goods_*` をリセットすること。過ぎたタイムスタンプを返しては絶対にいけない。

## 5. 方法論：traceback の行番号はバイトコードの行テーブルで変換しないと使えない

**ljd でデコンパイルした `.lua` の行番号は実行時行番号ではない**（本プロジェクトで 2 回踏んだ。2 回目でようやく完全に訂正した）。
実行時スタックの行番号はバイトコード自身の行テーブル由来で、`.bdl` を直接読む必要がある：

```python
env = UnityPy.load(bundle)
for o in env.objects:
    if o.type.name == 'TextAsset':
        raw = o.get_raw_data()          # 序列化对象的原始字节
        # proto.debuginfo.addr_to_line_map 给每条指令的原始行号
```

`tools/pfind.py`（どの関数がどの行範囲をカバーするか + その文字列定数）、`tools/pseq.py`、`tools/palign2.py`
はまさにこのためのもの。これがあれば「どの文でクラッシュしたか」は**読み出す**情報で、勘で当てるものではない。

## 6. アセット投入：FUSE、権限、そして 2 つの勘違い

- 既存の FUSE 宛先への `adb push` は**宛先を消しながら成功と報告する**ことがある。規則：まず
  `/data/local/tmp` へ push、それから `cp` で `Android/data/.../files/` へ入れる。
- `tar x` で展開したディレクトリは `0770 shell`。app（other ビット）に `x` がない → Unity が
  `Unable to open archive file`。修正：`find . -type d ! -perm -o=x -exec chmod o+x {} +`。
- **任意コンテンツダウンローダはディレクトリの書き込み権も必要**：クライアントは `System.IO.File.Replace`
  でダウンロードを確定する。`o+x` だけでは 77 MB 転送後に `UnauthorizedAccessException` が飛び、
  クライアントはそれを「ネットワーク接続が切断された」と報告する。
  書き込み権は `videos/` と `videos/optional/` の 2 ディレクトリだけ与える。mass-chmod はしないこと。
- `.bdl` には 40 バイト大文字 SHA-1 の `.bdl.hash` サイドカーが必須。ファイル権限 `0660` は詰まり要因ではない。触るな。
- manifest は AES-CBC の gzip。bundle を差し替えたら Hash と Size の両方を同時に変える（`tools/manifest_repoint.py`）。
  **ShortHash は内容から派生していない。触るな。** story パッケージは manifest にそもそも無い。`.bdl.hash` の差し替えだけでいい。
- manifest の `EncryptKey` が非ゼロなのにファイルが平文 UnityFS だと `Unable to read header from archive file`
  ——あの int32 をその場でゼロにしたのが、カード画像が全滅した真因。

## 7. ストーリーテキストの実際の置き場所と再パッケージ

- ステージ台詞は**言語テーブルに無い**：`resources/story/*_scene.bdl` 631 本がそれぞれ `_language` TextAsset を持ち、
  中身は `{"Key":[...],"Value":[...]}` の JSON。総量 46,277 行、うち約 3.08 万行は依然として日本語。
- **このアセット群に対して UnityPy の `m_Script` は非可逆**：UTF-8 でデコードするが payload は Shift-JIS で、
  CJK が全部 `?` になる。唯一信頼できる読み方は `obj.get_raw_data()` の中から JSON 文書を切り出すこと。
  （この罠で語料全体が文字化けのまま翻訳パイプラインに流れ込みかけた。）
- 中国語は Shift-JIS に入らない。書き戻し時は JSON を `ensure_ascii=True` で `\uXXXX` エスケープ出力：バイトは純 ASCII、
  utf-8/shift_jis/cp932 のどれでも同じ中国語文字列にデコードでき、エンコーディング問題そのものが消える。
- 保存は `env.file.save('original')` で元の圧縮を維持しないと、体積が 6 倍に膨らむ（223 KB → 1.37 MB）。

## 8. 簡体字中国語パイプライン

- 言語テーブルのインストール版：30,687 行 + `Terms` 8 行、コードポイントレベルで仮名 0、U+FFFD 0。
- **字形ゲート**：クライアントのフォントは `glyphset.txt` のあのリストではない（日本語原文自体がリスト外の 232 字を含み、それ表示できている）。
  判定基準は `glyphset ∪ ASCII ∪ その行の日本語原文の文字`。範囲外は豆腐ブロック。
  このゲートで実際「言い回しは綺麗だがグリフが無い」採用 27 件を弾いた（瑕／淇／噗／缥／萦／萃／哒／诶／彗／沁／痣／咻／嗖／×）。
- 成果物フォーマット：AI ワークフローの返送は `id<TAB>訳文` のプレーンテキスト。長いエントリは孤児行を吐き出す。規則は、まず前の行へ吸収させてから折り返しを畳む
  （言語テーブルの値に改行があっては絶対にいけない）。
- 一貫性：翻訳エージェントには納品済み語料から抽出した**確定セリフ表**（JP→CN、4,201 件）+ 用語表 + グリフリストを渡す。
  全量ファイルを読ませるやり方はしない。

## 9. 検証規律（この文書で一番価値のある項目）

- **コンソールの文字化けはデータの破損ではない**。まず対照実験で切り分ける（同じデータを Read ツールで読む／ファイルへ書いてから読み戻す）。結論はその後。
  本プロジェクトでは表示問題をデータ問題と誤ったことが 2 回ある。
- 判定根拠は自分で入力を偽造できること。常に 0 のカウンタ、拍子木のように決まった周期で出るログ行、どちらも証拠ではない。
- 数値を報告するならノイズフロアを添える：同一対象を繰り返し測定した差分。なければ「3 改善」は意味を持たない。
- 「ある原因は除外した」と言う前に、除外したのがその原因のこの経路上の形かどうか確認する。
- 納品前に足場を剥がす：診断ファイルゲート、SQL/RX/XE プローブ、`hide_error_dialogs`、`javax.net.debug`、
  REQDIAG/SIGRAW/MemDump 系の一時出力、全部ビルドから除去する。

## 10. ページの所在判定：プロトコル番号だけを信じ、スクショを信じない

未マッピングのプロトコルは全ゼロの応答が返るだけなのに、ページは**通常どおりレンダリング**される。中身が
空なだけだ。だから「ページが開いた」は「ページにデータがある」を意味しない。スキャン結果には 2 つを必ず
記録する：そのクリックが実際にどのプロトコル番号を発火させたか、その期間にクライアントが例外を何回報告したか。

- `P9000` と `P1021` は 60 秒のハートビート。踏んだ形状は「ボタンを押した → ログは確かに動いた → 合格と
  判定」だった。しかしあの 2 行はただのハートビートだった。「クリックが効いたか」の判定は必ず
  ハートビートを除外できること。
- アートカードのクリック可能領域はたいていテキストの中心にない。実測ではカード面のヒットボックスは
  ラベル中心から**右に約 40 px ずれている**。
- コールドスタートはスタブ自身のログで駆動し、固定時間の sleep は使わない。200 s 寝てから闇雲にクリック
  した版は、2 回目の再起動時にクライアントは実際まだタイトル画面にいて、レポートの後半が報告していたのは
  クライアントが一度も到達していないフレームだった。

## 11. クライアントのゲートは 2 か所だけ：`PlayerInst` と `Newbie`

- 通貨残高も所有物も例外なく `PlayerInst` を読む。`items[]` に 1 行突っ込むのは**惰的**——UI は変わらない。
  輝聖石のような課金通貨は `diamondPay` に植える必要がある。
- 機能解放は `Newbie` を読む。条件の形状は「レベル到達」または「あるステージクリア済み」。だから
  「あるページに入れない」はまず `Newbie` を疑い、サーバー側の権限フィールドを推測しに行かないこと。
- 価格には 2 列あって役割が違う。`GoodsPrice` は角バッジの表示専用、実際に `GetCost` / 支払可能判定 / 課金に
  使われるのは `CostValue`。2 列が不一致だと、クライアントは「1980 表示、0 課金」またはその逆をする。

## 12. 実行中のマスターデータは SQLite なので、挙動はデータ側で変えられる

`luaData/*.lua` はロジックではなくローダ。中で走っている実体は `select * from X`。だから挙動スイッチ
（あるページが使えるか、ある機能が解放されるか）はほとんどが**データ側**の直し方で、コードセグには触らない。

`Seed` の自己修復の判定基準は**ファイルの存在**で、ファイルダイジェストの一致ではない。だから修正済みの
`master_data.db` をデバイスに入れる正しいやり方は「ステージングに落としてから `cp` でアプリディレクトリへ」で、
APK の再ビルドではない——再ビルドは pin チェーンを全部やり直しにする。

## 13. サーバーのタイムスタンプがパネルを自己パージさせる

`PageShop` は `OnEnter` の途中で `freshAt` / `EndTime` の期限切れを理由に自分を purge する。症状は
「タップして一瞬光って消える。エラーは一切なし」。オフラインサーバーではこの 2 フィールドを一律 `0` で
返す。同様に、クライアント traceback の行番号は**バイトコードの行テーブルで変換しなければ**使えず、
Lua の行番号を直接読むと別の関数に連れて行かれる。

## 14. サイドカーと「欠落は完全にサイレント」

`.bdl` / `.bnk` の隣にある 40 バイトのダイジェストファイルはメタデータではなくロードゲート。実測ルールは
2 つ：`.bnk.hash` はちょうど 40 バイトの大文字 SHA-1、改行**なし**。`.bdl.hash` は **41 バイト**
（改行あり）。両者を「統一」するとリソースのロードが直接死ぬ。

アセット欠落の現れ方は層別。SoundBank の欠落は**全体サイレント**（エラーなし、ダイアログなし、ログに
痕跡なし）。bundle の欠落だけが `Unable to read header from archive file` を出す。しかも同じ症状文字列に
根因が 2 つある。manifest の `EncryptKey` がヘッダ XOR であるケース（非ゼロ key + 平文 UnityFS ファイルは
まさにこの症状になる）。そして上流が最初から 0 バイトだった bundle——だから**まずサイズ、次に鍵**。

## 15. 「動いたのが自分が直したあれ」を証明する

直したら、まず成果物に変更が入っていることを証明してから、結果を報告するか計測を始める。踏んだ 3 つは
それぞれ別：

1. 書き込みはサイレントに失敗しうる（ツールは成功と報告するが、ファイルの中身は変わっていない）。`grep -c`
   で対象識別子を**ファイル本体**から読み戻す。
2. ビルド失敗の後、私はやっぱりインストールした。コマンドを `build > log; install` の改行順で書いていた
   ため、ビルドは死んだのに install は走り、前のラウンドの古い APK をデバイスに入れて新パッケージとして
   テストした。`adb` は `Install command complete` まで返した。**インストールはビルド成功と同じ条件
   チェーンにしなければならない**（`build && install && test`）。入れた後、パッケージ内アセットのダイジェストと
   dex 内の新リテラルを比較する——`Install command complete` が証明するのは「どこかのパッケージが
   入った」ことで、「これが入った」ことではない。
3. スクリプトを直した直後に古い状態で測り、「前後で完全に同一」が出て、それを根拠に正しい解法を殺した。

対応するビルドの性質：ビルドは**ビット単位で再現可能ではない**（zip のタイムスタンプがパッケージに
入る）。だから全パッケージハッシュは身分に使えず、比較できるのはパッケージ内アセットだけ。

## 16. 判定手段自体を先に検証する

- 差分で「良くなった」と判定する前に、同一対象を繰り返し測定した**ノイズフロア**を出す。同一フレームの
  2 回の差がまさにこの閾値。
- マスクが飽和した対照は証拠にならない（全画面差分＝何も識別できていない）。
- 最適解が探索境界に貼り付いているとき、それは現在のモデルを反証しているのであって、「答えを見つけた」の
  ではない。
- ガードの対照群は、そのガードが弾く入力タイプを**自分で偽造**できなければならない。「前のバージョンなら
  弾かれていたはず」は対照ではない。
- 常に 0 のカウンタ、拍子木のように決まった周期で出るログ行、死んだ CSS selector——全部黙って通る。
